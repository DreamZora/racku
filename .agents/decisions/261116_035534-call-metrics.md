# Decision: Call and event metrics

Status: accepted

## Background

- Under [Backplane protocol with direct links between devices](261116_024226-backplane-links.md), calls and events between devices travel on links between Workers, so the rack main thread no longer sees them and cannot count them.
- On 2026-11-16 the user asked to keep instrumentation for these calls where performance permits, such as call counts.
- Counting costs about 50 ns per call on each side, against 11 µs for the fastest round trip on a link (see [Evidence](#evidence)).

## Decision

### Counters

- Each instance's Worker host counts the calls and events of its device from boot until the instance exits. A swap or a reset starts a new instance whose counters start at zero.
- Every RPC member of a provided port counts the calls the device served, including calls from `rack.call` and the panel.
- Every event member of a provided port counts the events the device emitted.
- Every RPC member of a need counts the calls the device made.
- Every event member of a need counts the events the device received.
- There are no latency histograms.

### Reading

```ts
interface RackHandle {
  // ...the members of the P0 rack handle
  metrics(): Promise<RackMetrics>;
}

interface RackMetrics {
  devices: DeviceMetrics[];
}

interface DeviceMetrics {
  device: string;
  firmware: string; // hash of the instance that counted
  since: number; // millisecond timestamp of the instance's boot
  provides: Record<string, Record<string, ServedRpcMetrics | EmittedEventMetrics>>; // port -> member
  needs: Record<string, Record<string, CalledRpcMetrics | ReceivedEventMetrics>>; // need -> member
}

interface ServedRpcMetrics {
  kind: "rpc";
  calls: number;
  ok: number;
  errors: Record<string, number>; // error code -> count
  active: number;
  timeMs: number;
}

interface EmittedEventMetrics {
  kind: "event";
  emitted: number;
  dropped: number;
}

interface CalledRpcMetrics {
  kind: "rpc";
  calls: number;
  ok: number;
  errors: Record<string, number>; // error code -> count, RACK_TIMEOUT and RACK_CANCELLED included
  pending: number;
  queued: number;
  timeMs: number;
}

interface ReceivedEventMetrics {
  kind: "event";
  received: number;
}
```

- `metrics()` asks every installed instance for its counters over the control channel, in parallel, and resolves with one `DeviceMetrics` per device whose installed instance answered within `hookTimeout`, ordered by `u`. After `stop()` it resolves with no devices.
- The counters cross the control channel only when `metrics()` asks for them; nothing is sent otherwise.
- The fields mean the following:
  - `calls` counts calls started. `ok` counts calls that succeeded, and `errors` counts failed calls by error code.
  - `active` (served) and `pending` (made) count calls that have started and not finished. `queued` counts made calls that wait because the provider slot is held.
  - `timeMs` is the total duration of finished calls in milliseconds: from receipt to reply for served calls, and from the call to its result for made calls. The mean duration is `timeMs` divided by the number of finished calls.
  - `emitted` counts events whose payload passed validation. `dropped` counts deliveries that did not happen, either because the instance was not installed or because a held consumer's queue was full.
  - `received` counts events delivered to the device, however many handlers it has.

## Evidence

Measured on 2026-11-16 on Bun 1.4.4, Linux, 32 cores, with a probe script outside the repository:

- Over 20 million iterations, a function that only adds to a variable took 0.7 to 2.8 ns per call. The same function wrapped in two `performance.now()` reads, four counter updates, and an error-code map update on one call in 1024 took 51 to 53 ns per call.
- The fastest round trip measured for [Backplane protocol with direct links between devices](261116_024226-backplane-links.md#copy-cost) is 10.6 µs, so counting on both sides adds about 1% to it.

## Alternatives

- **Push counters into `status()` every few seconds**: `status()` would stay synchronous, but values would be up to one period old and the counters would cross the control channel all the time. The user chose reading on demand.
- **Latency histograms**: percentiles such as p99 need buckets per member, which cost more memory and more work per call. The user left them out; they can be added later.
- **Count on the main thread**: link traffic never reaches the main thread, so counting there would mean sending a message per call, the cost links remove.
- **Emit a trace event per call**: it also costs a message per call, and it is more than the call counts asked for.

## Impact

- Every call costs about 50 ns more on each side, and every event a few nanoseconds more, for counting.
- Counters restart when a device swaps or resets. A reader that needs totals across instances can tell instances apart by `firmware` and `since`.
- The rack handle gains `metrics()`, documented in `README.md` and tested.
- The planned breaker, thermal, and management controller can read these counters instead of collecting their own.

## Implementation

- Shapes: `src/metrics.ts`, exported from `src/index.ts`.
- Counting: `src/worker.ts`. `prepare` creates zeroed counters at boot. Calls made are counted in `callOut` and `settle`, calls served in `serve`, events emitted in `emitOut`, and events received in `deliver`. `snapshot` answers the `metrics` request.
- Reading: `metrics` of the rack handle in `src/rack.ts`, through `Instance.metrics` in `src/instance.ts`, with `hookTimeout` as the timeout of each request.
- Tests: `test/metrics.test.ts`. `queued` is checked by the held-slot test in `test/links.test.ts`. `README.md` documents the counters under "Running a rack".

## Confirmation

- On 2026-11-16 the user asked for instrumentation and, answering the Agent's question, chose reading on demand through `rack.metrics()`, with counters for calls served, calls made, and events, and without latency histograms.
