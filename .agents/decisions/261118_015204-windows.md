# Decision: Windows as a supported platform

Status: accepted

## Background

- No decision made Windows a supported platform. [Continuous integration on main and on request](261117_182058-ci-on-main-and-on-request.md) runs the tests on Windows, but only to report. Only the management endpoint has Windows defaults: loopback TCP with a token, and a control file under `%LOCALAPPDATA%`, as [Management endpoint and the rack ctl command](261117_005821-management-endpoint.md#transports) decides.
- On 2026-11-18 the user asked that Windows be supported.
- The Windows job of the run on `main` at `00acd8c` passed 354 tests, skipped 17, and failed 12. No failure is a fault in the rack's logic. Each comes from an assumption that holds on Linux and macOS only:

  | Failures | Cause |
  |---|---|
  | 7: the signal tests of `rack start` and `rack dev`, and the shop-api example | Bun's `kill()` ends a Windows process at once, without a signal it can handle, so the rack never shuts down in order. |
  | 2 more in the shop-api example | Cleanup removes the app's directory right after a kill, while the process still runs, and Windows refuses to remove a directory in use. |
  | 1: the bin test | It links `node_modules/.bin/rack` to `src/cli.ts` and relies on its `#!` line, which Windows doesn't run. |
  | 1: the README's hello app | Git checks files out with CRLF on Windows, so the test finds no code blocks. |
  | 2: a swap to another file, and the crash log's source map | The tests expect `/` in paths that Windows writes with `\`. |

- Of the 17 skipped tests, the 12 tests of threads stuck in native code block a thread with a FIFO, which Windows lacks. 2 protocol tests reach the endpoint by its Unix socket, and 3 tests are about the Unix socket itself.
- Goals, as [Design goals and principles](261117_062916-design-principles.md#goals) defines them: reliability, since the rack's guarantees then hold, and are tested, on one more system; and extensibility, since builders on Windows can use the framework.

### Evidence

Measured on 2026-11-18 by a probe run on GitHub's `windows-latest` runner, Windows Server 2025 (10.0.26100), with Bun 1.4.4. The probe is not in the repository.

- Git's system configuration sets `core.autocrlf=true`, and the checkout of `README.md` and `src/cli.ts` had CRLF line endings.
- A Worker reading a named pipe that the main thread serves blocks in the read. After `terminate()`, its thread had not ended 1.5 s later. It ended 6 ms after the main thread closed the pipe, as a thread blocked on a FIFO does on Linux and macOS.
- `kill("SIGINT")` on a child that `Bun.spawn` started ended it with exit code 130 before its `SIGINT` handler ran.
- Console control events reach a Bun process as signals. Ctrl+C arrived as `SIGINT`, whether Bun, `node:child_process`, or `CreateProcessW` had started the child. Ctrl+Break arrived as `SIGBREAK`. Each child ran its handler and exited with 0.
- The processes of a CI job have no console. A process that allocates one with `AllocConsole` can send these events with `GenerateConsoleCtrlEvent` to the processes on that console, which no other process of the job shares.
- Once a killed process that held a SQLite database open in WAL mode had exited, its directory could be removed within 3 ms, whether it had been the process's working directory or not.
- `bun install` of a `file:` dependency on this repository crashed Bun ("The supplier of fd FD should call 'FD.makeLibUVOwned'"), so the probe did not show what `bun install` writes to `node_modules/.bin`.

## Decision

### What supported means

- Windows on x64, as GitHub's `windows-latest` runner provides it, is supported as Linux and macOS are. What the README describes works there and is tested there, except for the differences the README states.
- The Windows job of CI fails the workflow, as the macOS job does. [Continuous integration with Windows checked](261118_015210-ci-with-windows.md) replaces the CI decision for this.
- The development commands, such as `bun run check`, are checked on Linux only, as the CI decision already decides; `bun test` is checked on all three systems.

### Differences the README states

- **The management endpoint:** loopback TCP with a token, as already decided. There is no Unix socket.
- **File modes:** Windows has none. The control file is private because it lives under `%LOCALAPPDATA%`, which belongs to the user.
- **Stopping in order:** Ctrl+C, Ctrl+Break, and `rack ctl stop`. Windows has no `SIGTERM`. A process ended from outside, such as by Task Manager, `taskkill /F`, or Bun's `kill()`, ends at once, as with `SIGKILL` elsewhere. Closing the console window ends the rack as a hangup does elsewhere.
- **Paths:** the rack reports paths with the system's separator, such as `source` in `status()`. Manifests may write relative paths with `/` on every system.

### Changes to the rack

- `rack start` and `rack dev` also shut down in order on `SIGBREAK`, which Ctrl+Break sends on Windows. A second signal of any of the three exits at once with code 1, as it does now for `SIGINT` and `SIGTERM`.

### Changes to the repository and the tests

- A `.gitattributes` makes every checkout use LF line endings, so the files, and the firmware built from them, are the same on every system.
- A test of a platform facility runs wherever the facility exists, with the same expectations, as the CI decision requires. On Windows:
  - A test that stops a `rack` process in order sends it Ctrl+C or Ctrl+Break, through a helper process that owns a console. The `SIGTERM` test runs on Linux and macOS only.
  - The tests of threads stuck in native code block the thread on a named pipe instead of a FIFO.
  - The protocol tests reach the endpoint over TCP.
  - The Unix socket tests still run on Linux and macOS only.
- Tests build the paths they expect with `node:path`. Cleanup waits for a killed process to exit before it removes the process's directory.
- The bin test runs the `rack` command through what a real install of the package writes to `node_modules/.bin`. The implementation finds an install that works on Windows, since a `file:` dependency crashes Bun 1.4.4 there.

## Alternatives

- **Keep Windows reporting only**: builders on Windows get no guarantee, and a regression there goes unnoticed.
- **Support Windows through WSL only**: nothing to change, since WSL runs Linux. But the rack would still not run on Windows itself.
- **Stop in order on Windows only through `rack ctl stop`**: the tests would need no console helper. But Ctrl+C, which is how a console user stops a program, and how service wrappers such as NSSM stop one, would stay untested, and the README could not promise it.
- **Call the shutdown directly in tests instead of sending Ctrl+C**: simpler, but nothing would then test that the events reach the rack.

## Impact

- The README states that Windows is supported, with the differences above, and no longer calls the Windows job report-only. The Ctrl-C and signal sentences cover Windows.
- `AGENTS.md` lists this decision under the current state.
- A failure in the Windows job now fails the run. The job's cost doesn't change: it already ran on every push to `main` and every manual run.
- The tests gain a Windows helper that owns a console and sends console events through `kernel32.dll` with `bun:ffi`. It is test code only: the rack itself gains no native code.
- Follow-up work once this decision is accepted:
  - `src/cli.ts`: `SIGBREAK`, with tests on Windows.
  - `.gitattributes`, and the test changes above, until the Windows job passes.
  - `.github/workflows/check.yml`, as the replacing CI decision decides.

## Confirmation

- The user accepted this decision on 2026-11-18, after asking that Windows be supported.
