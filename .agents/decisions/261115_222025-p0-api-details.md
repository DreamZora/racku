# Decision: P0 standard connectors, rack handle shapes, and test fixtures

Status: accepted

## Background

- [P0 scope, repository layout, and toolchain](261115_232410-p0-scope-and-toolchain-bun-1-4-4.md#p0-scope) ships the standard devices `memkv` (`kv/v1`) and `sqlite` (`sql/v1`), but no decision defines the members of either connector. [Device and rack API](261112_043034-device-api.md#connectors) shows a `kv/v1` only as an example of the connector API.
- The device and rack API names the methods of the rack handle, the `logger` option, and the timer helpers of `scope`, but leaves their data shapes open.
- The decisions do not say which error code covers a problem found while a swap runs, how a crash during a reset or a swap is handled, or how names are restricted so that `<device>.<port>` addresses stay unambiguous.
- Tests need device files and rack manifests to mount, and some tests edit device files to exercise hot reload. The P0 layout gives `test/` only to `*.test.ts` files.

## Decision

### Standard connectors

`rack42u/std` exports `Kv` and `Sql`:

```ts
export const Kv = connector("kv/v1", {
  get: rpc(v.string(), v.nullable(v.string())),
  set: rpc(v.object({ key: v.string(), value: v.string() }), v.undefined()),
  delete: rpc(v.string(), v.boolean()),
  keys: rpc(v.string(), v.array(v.string())),
  changed: event(v.object({ key: v.string() })),
});

const SqlValue = v.union([
  v.string(), v.number(), v.bigint(), v.boolean(), v.null(), v.instance(Uint8Array),
]);
const Statement = v.object({ sql: v.string(), params: v.optional(v.array(SqlValue)) });
const RunResult = v.object({
  changes: v.number(),
  lastInsertRowid: v.union([v.number(), v.bigint()]),
});

export const Sql = connector("sql/v1", {
  query: rpc(Statement, v.array(v.record(v.string(), SqlValue))),
  run: rpc(Statement, RunResult),
  batch: rpc(v.array(Statement), v.array(RunResult)),
});
```

- `kv/v1` keeps the `get`, `set`, and `changed` members of the example in the device API decision and adds `delete` and `keys`.
  - Values are strings; callers encode structured values themselves, for example as JSON.
  - `delete` reports whether the key existed.
  - `keys(prefix)` returns the keys that start with `prefix`, sorted; `""` returns every key.
  - `changed` is emitted after every `set`, and after a `delete` that removed a key.
- `sql/v1`:
  - `params` bind to positional `?` placeholders.
  - `query` returns rows as objects keyed by column name.
  - `run` returns the number of changed rows and the last inserted row id.
  - `batch` runs its statements in order inside one transaction; when one fails, the transaction rolls back and the call fails.
  - A database error fails the call with the device error code `SQL_ERROR` and the driver message; `data.code` holds the driver's error code when it has one, for example `SQLITE_CONSTRAINT_UNIQUE`.

### Standard devices

- `memkv(options?)` mounts the `memkv` device, which provides `kv: Kv` and keeps its entries in memory.
  - Entries move to the new instance through `snapshot`/`restore` during a swap or a hot reload; a crash reset or a restart loses them.
- `sqlite(config, options?)` mounts the `sqlite` device, which provides `sql: Sql` through `bun:sqlite`.
  - `config.path` is the database file, relative to the rack base directory; `":memory:"` opens an in-memory database. Missing parent directories are created.
  - A file database uses WAL journal mode and a 5-second busy timeout, so the old and the new instance can both hold it open during a swap.
  - An in-memory database moves to the new instance through `snapshot`/`restore` as a serialized image.
- `options.name` sets the device name; it defaults to the model name.
- Both factories return only a mount description, as the device API decision requires.

### Names

- A device name matches `^[A-Za-z0-9][A-Za-z0-9_-]*$`. When the model name serves as the default device name, it must match too.
- The keys of `needs` and `provides` follow the member name rule of connectors.
- Both rules keep `<device>.<port>` addresses unambiguous.

### Device hooks

- A device without a `config` schema receives the configuration as given in `ctx.config`, or `undefined` when there is none.
- A device without `provides` may omit `powerOn`. Otherwise `powerOn` must return a function for every RPC member of every provided port, or it fails.
- `selfTest(ctx)` fails when it throws or its Promise rejects.
- On `deactivate`, the rack aborts `scope.signal` and stops the timers of `scope` before it calls the device's `deactivate` hook.
- On `powerOff`, the rack calls the device's `powerOff` hook and then aborts `ctx.signal`.
- `scope.every(ms, task)` and `scope.after(ms, task)` return a function that cancels that timer. `every` waits for an asynchronous task to settle before it schedules the next run, so runs never overlap.
- `ctx.emit.<port>.<event>` rejects with `RACK_INVALID_OUTPUT` when the payload fails validation or cannot be cloned, because an event payload is output of the publishing device.

### Rack handle

```ts
interface SlotStatus {
  name: string;
  model: string;
  u: number;
  height: number;
  state: "online" | "swapping" | "degraded" | "resetting" | "faulted";
  firmware: string | null; // hash of the installed instance; null when none is installed
  source: string; // absolute path of the device file
  inFlight: number; // calls the installed instance is processing
  crashes: number; // crashes within the last 60 seconds
  error?: WireError; // the last failed swap or crash
}

interface LogEntry {
  time: number;
  level: "debug" | "info" | "warn" | "error";
  device?: string; // absent for entries written by the rack itself
  message: string;
  data?: unknown;
}

type RackEvent =
  | { type: "power"; device: string; firmware: string; state: "on" | "off" }
  | {
      type: "swap";
      device: string;
      action: "plug" | "unplug" | "swap";
      from: string | null;
      to: string | null;
      error?: WireError;
    }
  | { type: "fault"; device: string; firmware: string; error: WireError; reset: boolean }
  | ({ type: "log" } & LogEntry);

interface ReloadResult {
  device: string;
  from: string | null;
  to: string | null;
  error?: WireError;
}
```

- `status()` returns one `SlotStatus` per device, ordered by `u`.
  - `swapping`: a swap is running, and the old instance, if there is one, keeps serving.
  - `degraded`: the last swap failed and the old instance keeps serving.
  - `resetting`: the instance crashed and a reset is running; calls fail with `RACK_LINK_DOWN`.
  - `faulted`: resets stopped after too many crashes; calls fail with `RACK_LINK_DOWN` until a swap succeeds.
- `subscribe(listener)` returns a function that removes the listener. Errors thrown by a listener are ignored.
  - A `power` event is sent when an instance starts serving (`on`) and when a retired instance has powered off (`off`).
  - A `swap` event is sent for every `swap`, `plug`, and `unplug`, and for every device that `reload` tries to swap; `error` is present when the swap failed.
  - A `fault` event reports a crash; `reset` is `false` when the slot is marked faulted instead of reset.
  - A `log` event carries every log entry.
- The `logger` option is a function that receives every `LogEntry`. The default writes one line per entry to the console.
- `swap`, `plug`, and `unplug` resolve once the operation has finished, including the retirement of the old instance. On failure they reject with a `RackError` after rolling back.
- `reload()` resolves with one `ReloadResult` per device whose firmware hash changed or whose firmware failed to build, in the order the devices were swapped, bottom up. A failed device carries `error` and does not stop the others.
- Management operations (`swap`, `plug`, `unplug`, `reload`, and `stop`) run one at a time, in the order they were called.
- After `stop()`, `call` fails with `RACK_LINK_DOWN`, management operations fail with `RACK_SWAP_REJECTED`, and `status()` returns an empty array.
- When the HTTP panel opens, the rack logs `panel http listening` with `data.url`, so a manifest can use port 0 and still be reached.

### Error codes

- At start, a device file that fails to build, fails to load, or does not default-export a device fails with `RACK_MANIFEST`. During a swap, the same problems fail with `RACK_SWAP_REJECTED`.
- Layout and wiring problems fail with `RACK_MANIFEST`, at start and during a swap: overlapping slots, exceeded capacity, the gravity rule, missing or ambiguous wiring, duplicate names, and patches or panel routes that name an unknown device or port.
- The compatibility check of a swap fails with `RACK_SWAP_REJECTED`: a port that is wired or referenced by a panel route disappears, changes connector, or loses a member that a consumer needs. Unplugging a device that is still wired or routed, and a management operation on a slot whose reset is running, fail with the same code.
- `swap` and `unplug` with an unknown device name fail with `RACK_NO_ROUTE`.
- When the slot is paused for a state handover and in-flight calls do not finish within `drainTimeout`, the swap rolls back with `RACK_SWAP_REJECTED`.

### Resets

- Calls that arrive while a reset runs fail with `RACK_LINK_DOWN`.
- A reset that fails at boot, `powerOn`, `selfTest`, or `activate` counts as another crash, so a device that cannot start stops resetting at the crash limit of the backplane protocol.
- When the installed instance crashes while a swap of its slot runs, the swap skips the steps that need the old instance. If the swap then fails, the slot resets from the old firmware, or is marked faulted at the crash limit.

### Command line

- `rack start` and `rack dev` use the manifest's directory as the base directory.
- `rack dev` watches the base directory recursively, ignoring `node_modules` and dot directories, and calls `reload()` 100 ms after the last change. When the manifest file itself changes, it logs a warning that the change takes effect after a restart.
- Both commands exit with code 1 when the rack fails to start, and with code 0 after an orderly shutdown. A second `SIGINT` or `SIGTERM` during shutdown exits at once with code 1.

### Test fixtures

- `test/fixtures/` holds device files, rack manifests, and helper modules that tests import. Nothing there is named `*.test.ts`, and the files are type-checked and linted like the rest of the code.
- Tests that edit device files copy them into a temporary app directory outside the repository, whose `node_modules/rack42u` links to the repository root.

## Alternatives

- **Accept any structured-cloneable value in `kv/v1`**: `v.unknown()` would hand callers untyped data, and the accepted example already uses string values. Callers that need structure encode it.
- **Interactive transactions in `sql/v1` (`begin`/`commit` calls)**: a transaction would span several backplane calls, and a swap or a crash between them would leave it open. `batch` gives atomic multi-statement writes within one call.
- **Named parameters in `sql/v1`**: positional parameters cover the same needs with one rule.
- **Resolve `swap` before the old instance is retired**: callers and tests could not tell when the old instance had powered off.
- **Reject `reload()` when one device fails**: one broken device would hide the results of the others, which matters most in `rack dev`.
- **Expose the panel address on the rack handle**: it adds a handle member that the device API decision does not list, while a log entry carries the same information.
- **Queue calls while a reset runs**: callers would wait up to their timeout for a device that may never come back; failing fast with `RACK_LINK_DOWN` matches the meaning of that code.
- **Write test app directories inside the repository**: a crashed test would leave edited files in the working tree.

## Impact

- `kv/v1` and `sql/v1` are bound by this decision; incompatible changes need new connector ids.
- `memkv` loses its entries on a crash reset or a restart, as the backplane protocol decision anticipates for in-memory state.
- Running management operations one at a time keeps swaps simple at the cost of parallel swaps, which P0 does not need.
- Edits outside the base directory, such as edits to the standard devices themselves, do not trigger a reload in `rack dev`.
