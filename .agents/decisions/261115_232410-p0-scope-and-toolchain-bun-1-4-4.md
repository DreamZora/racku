# Decision: P0 scope, repository layout, and toolchain on Bun 1.4.4

Status: accepted

## Background

- The architecture and the hot swap mechanism are settled ([Rack runtime architecture](261112_035942-rack-architecture.md), [Every device supports hot swap and hot reload](261112_035943-hot-swap.md)), and the first runnable version is needed to validate them.
- [P0 scope, repository layout, and toolchain](261112_043033-p0-scope-and-toolchain.md) fixed how far P0 goes, where code lives, and which tools are used, with Bun 1.3.13 as the minimum version.
- While the backplane was implemented, Bun 1.3.13 proved to crash the whole process when a Worker that exchanged messages over a transferred `MessagePort` ends (see [Evidence](#evidence)). The [Backplane protocol](261112_043035-backplane-protocol.md#channels) requires exactly such a `MessagePort` for the data channel, so on 1.3.13 one device crash or swap can take down the rack.
- This decision replaces the earlier one. Its content is unchanged except for the Bun version and the evidence.

## Decision

### P0 scope

P0 delivers the smallest rack that is actually usable, with the following:

- **Definition entry points**: connectors, devices, and the rack manifest (API in [Device and rack API](261112_043034-device-api.md)).
- **Installation forms**: `sled` only, one Worker per device.
- **Backplane**: RPC, events, timeouts, cancellation, and error propagation (protocol in [Backplane protocol](261112_043035-backplane-protocol.md)).
- **Firmware build**: each device is built separately with `Bun.build`, and the content hash is the version.
- **Startup and shutdown**: cold start and shutdown power devices on and off in slot order; assembly validates slot overlap, capacity, the gravity rule, and wiring.
- **Swap**: reload, insert, remove, and replace go through one process, including `snapshot`/`restore` state handover and rollback on failure.
- **Crash reset**: a device is reset automatically after it crashes; the policy is in the backplane protocol decision.
- **Panel**: provides an HTTP port and forwards requests to devices through the `http/v1` connector.
- **Development mode**: watch file changes and swap only the devices whose firmware hash changed.
- **Standard devices**: `memkv` (provides `kv/v1`) and `sqlite` (provides `sql/v1`).
- **Command line**: `rack start` and `rack dev`.
- **Decision gate**: a script that checks the format of decision files and the `@decision` references in code.
- **Example and documentation**: the example app `examples/shop-api` and `README.md`.

The following is not in P0 and is left for later stages:

- The `inline` and `chassis` installation forms.
- Editing the rack manifest while the rack runs (reconcile). In P0, changing the manifest requires restarting the rack.
- Batch swaps that replace several devices at once. In P0, changing a connector's version requires restarting the rack.
- The WebSocket panel, breaker, thermal, watchdog, management controller dashboard, and top-of-rack switch.
- More standard devices, the single-device test bench, and `bun build --compile` packaging.

### Repository layout

- The repository root is the only npm package, named `rack42u`.
- Directories:
  - `src/`: framework source. `src/index.ts` is the entry point of `rack42u`, and `src/std/index.ts` is the entry point of `rack42u/std`.
  - `test/`: `bun:test` tests, named `*.test.ts`.
  - `examples/`: example apps.
  - `scripts/`: project scripts, such as the decision gate.
- TypeScript source is published directly, without precompilation. The command-line entry `rack` points to `src/cli.ts`.
- Files generated by the rack runtime go in `.rack/` under the app directory and are not committed to version control.

### Firmware build

- Each device file is built with one separate `Bun.build` call, with these options:
  - `target: "bun"`
  - `sourcemap: "inline"`
  - `naming: "[name]-[hash].[ext]"`
- Output goes to `.rack/firmware/` under the rack base directory.
- Firmware must live inside the app directory. The reason is that external imports in firmware keep bare package names and resolve through the app's own `node_modules`, so outside the app directory they cannot be resolved.
- The external list:
  - The framework itself (`rack42u`).
  - Every dependency declared in the `package.json` closest to the device file, including dependencies, devDependencies, peerDependencies, and optionalDependencies.
  - Package subpaths (for example `rack42u/std`) also stay external.
- Everything else is built into the bundle, including files reached through tsconfig path aliases, so editing those files also triggers hot reload.
- The firmware version is the hash in the file name produced by `Bun.build`.

### Toolchain and dependencies

- The runtime, the package manager, and the test runner are all Bun, minimum version 1.4.4, declared in `engines.bun`.
- Type checking uses `tsc --noEmit` with `strict` enabled.
- Formatting and static checks use Biome.
- Runtime dependencies:
  - `valibot`: writes schemas for the connectors the framework ships (`http/v2`, `kv/v1`, `sql/v1`).
  - `@standard-schema/spec`: type definitions for Standard Schema.
- Development dependencies:
  - `typescript`, `@types/bun`, `@biomejs/biome`.
  - `zod`: used only in tests, to verify that Standard Schema libraries other than valibot also work.
- Versions:
  - `valibot` 1.5.0, `@standard-schema/spec` 1.1.0, `zod` 4.6.7, in use from 2026-11-12.
  - `typescript` 7.0.2 and `@biomejs/biome` 2.6.7, in use from 2026-11-12.
  - `@types/bun` 1.4.4, matching the Bun baseline, in use from 2026-11-15.
- All of these dependencies are licensed MIT or Apache-2.0.
- `bun.lock` is committed.

### Commands

- `bun test`: runs the tests.
- `bun run typecheck`, `bun run lint`, and `bun run check:decisions`: run type checking, static checks, and the decision gate respectively.
- `bun run check`: runs all of the above checks in order.

### Documentation

- Project documentation under `README.md` and `docs/` is written in American English.

## Evidence

Measured on 2026-11-12 on the local machine with Bun 1.3.13:

- With `Bun.build` set to `packages: "external"`, tsconfig path aliases are preserved as external imports, and the code they point to is not built into the bundle.
- With `external: ["rack42u", "valibot"]` set explicitly, the code the alias points to is built into the bundle, while `rack42u`, `rack42u/std`, and `valibot` stay external.
- A bundle under the app directory's `.rack/firmware/` resolves `rack42u` and third-party packages through the app's `node_modules`, runs in both the main thread and a Worker, and receives the same framework module instance as the main thread.
- After the bundle is moved outside the app directory, `rack42u` cannot be resolved. Even when a plugin returns an absolute path from `onResolve` and marks it external, the generated code still writes the bare package name.
- Running `Bun.build` twice in a row on the same source yields the same output path and hash.
- With `sourcemap: "inline"` set, error stacks in a Worker point to the original `.ts` files and line numbers.
- When the framework package refers to itself through package self-reference (`import "rack42u"`), `tsc` resolves it correctly.

Measured on 2026-11-15 on the local machine, with probe scripts outside the repository:

- Bun 1.3.13: a Worker receives a `MessagePort` through the transfer list of `postMessage`, the two sides exchange 20 messages over it, and the Worker then ends. Over 240 such cycles, the process crashed with a segmentation fault or hung in nearly every run. This held whether the main thread terminated the Worker, the Worker called `process.exit`, or both sides closed their ports first; with `node:worker_threads` instead of the web `Worker`; with one Worker at a time; and when the Worker created the channel and transferred a port back. A transferred port without traffic, and traffic over the Worker's own `postMessage`, did not crash.
- Bun 1.4.4: the same scripts completed every run.
- Bun 1.4.4: the test suite re-checks part of the 2026-11-12 list. With the explicit external list, `rack42u`, `rack42u/std`, and `valibot` stay external while code behind a tsconfig path alias is bundled; the same source builds to the same path and hash (`test/firmware.test.ts`). A bundle under a temporary app's `.rack/firmware/` resolves `rack42u` through that app's `node_modules` in the main thread and in Workers (`test/firmware.test.ts`, `test/swap.test.ts`). A crash in a Worker is logged with the original `.ts` file (`test/reset.test.ts`). `tsc` resolves the self-reference (`bun run typecheck`). The `packages: "external"` behavior and the failure outside the app directory were not re-measured.

## Alternatives

- **Keep Bun 1.3.13 and carry every bus over the Worker's own `postMessage`**: it works on 1.3.13, but it needs new decisions that replace the channel rules of the backplane protocol and the rack architecture, management messages then queue behind data traffic, and device authors who use `MessagePort` themselves would still crash the rack on 1.3.13.
- **Split into core, std, and cli packages with a Bun workspace**: it means maintaining several package.json files, tsconfig files, and version numbers. At P0 scale, a single package with subpath exports is enough, and it can be split later when there is a real need.
- **Keep test files next to the source (`src/**/*.test.ts`)**: tests then have to be excluded separately when publishing. Keeping them together under `test/` is clearer.
- **Handle external dependencies with `packages: "external"`**: path aliases are mistaken for external packages, and code pulled in through an alias cannot hot reload (see "Evidence").
- **Write the framework's own connectors with zod**: it is larger. valibot supports on-demand imports, is small, and also supports Standard Schema natively.
- **Write a minimal schema library in-house**: validation logic and type inference then have to be maintained by hand, which is worse than a well-maintained existing library.
- **Prettier plus ESLint**: two tools and two configurations. Biome alone handles both formatting and static checks.
- **Precompile to JavaScript and publish that**: the framework runs only on Bun, and Bun executes TypeScript directly, so precompiling adds nothing but a build step.

## Impact

- Users and contributors need Bun 1.4.4 or later; Bun 1.3.x is no longer supported.
- The framework depends on valibot and `@standard-schema/spec`. Device authors can still define their own connectors with any library that implements Standard Schema.
- Third-party packages are not built into firmware, so after a third-party package is upgraded the rack must be restarted for the change to take effect.
- The rack base directory must be inside the app directory, otherwise firmware cannot resolve external dependencies.
- Documentation must state clearly which capabilities P0 does not support, so that they are not mistaken for supported ones.

## Implementation

- Toolchain: `package.json` (scripts, `engines.bun`, and dependencies), `tsconfig.json`, `biome.json`, and `bun.lock`.
- Decision gate: `scripts/check-decisions.ts`, run by `bun run check:decisions`.
- Entry points: `src/index.ts` (`rack42u`), `src/std/index.ts` (`rack42u/std`), and `src/cli.ts` (the `rack` command).
- Firmware build: `buildFirmware` in `src/firmware.ts`, tested in `test/firmware.test.ts`.
- Example and documentation: `examples/shop-api`, tested in `test/example.test.ts`; `README.md`, whose app is run by `test/readme.test.ts`.
- Tests: `test/*.test.ts`, with fixtures in `test/fixtures/`.

## Confirmation

- On 2026-11-15 the Agent reported the Bun 1.3.13 crash to the user with two options, raising the baseline to Bun 1.4.4 or moving every bus onto the Worker's own `postMessage`. The user chose to raise the baseline, which is this decision.
