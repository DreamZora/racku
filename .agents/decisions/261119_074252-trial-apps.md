# Decision: A skill for rack42u, trial apps built by independent agents, and their problems filed as GitHub issues

Status: accepted

## Background

- The documentation that [A README that explains rack42u, and complete documentation that tests hold to the code](261119_055008-documentation.md#what-comes-next) decides is in place, and its "What comes next" calls for this decision.
- On 2026-11-19 the user set the plan: "After the README and documentation are improved, write a skill for the rack42u project, choose some typical simple applications, and then have an independent Agent use rack42u to develop them. Record the problems encountered during that process, file them as issues (the issue templates need to be written first), and then solve and optimize them together." And: "When I said record issues, I mean filing issues on the GitHub repository."
- Asked how the agents should run, the user chose a workflow, saved in a trials folder and run from a Claude Code session started there. The Agent first proposed that folder outside the repository; the user answered: "I don't think putting it outside the repo is a good idea, since it wouldn't fully capture the evolution history of rack42u. Which directory in the repo should it go under? I'll open a new Claude in that directory. The prerequisite is that you need to write the .gitignore properly so unnecessary files aren't tracked."
- What there is on 2026-11-19:
  - The repository on GitHub is private, with issues enabled, no issue templates, and GitHub's default labels, `bug`, `documentation`, and `enhancement` among them.
  - An app depends on rack42u through git, and a git install copies the whole repository into the app's `node_modules/rack42u/`, the documentation included, and `CLAUDE.md` as a copy of `AGENTS.md`.
  - Writing the getting-started guide found one problem that a builder would meet: a call to an RPC member without input needs an explicit `undefined`. Others are likely.
  - In this repository, `bun test` and the decision gate skip dot directories, as a probe of `bun test` showed on 2026-11-19; the type check covers only `src/`, `test/`, `examples/`, and `scripts/`; and Biome checks every file that git doesn't ignore. The root `.gitignore` ignores `node_modules/`, `.rack/`, logs, and `*.sqlite`, but not `*.db`.
- What Claude Code 2.1.322 does, from its documentation:
  - A session loads `CLAUDE.md` from the directory it starts in and from every directory above it, and the `CLAUDE.md` of a subdirectory once it reads a file there. The setting `claudeMdExcludes` skips the `CLAUDE.md` files whose absolute paths match its globs, such as `**/rack42u/CLAUDE.md`.
  - The agents of a workflow get the `CLAUDE.md` files of the session that runs it. A session started in a folder of this repository would give them this repository's `AGENTS.md`, which describes how rack42u works inside, and whose rules, such as writing a decision before any implementation, are for work on rack42u, not on an app; unless that folder's settings exclude it.
  - A session reads its project settings from the `.claude/settings.json` of the directory it starts in. It finds saved workflows in the `.claude/workflows/` of that directory and of the directories above it, and skills likewise, a skill directory that is a symbolic link included.
  - The permission mode `dontAsk` runs the tools that the allow rules list without a prompt, and reads in its directory and read-only commands as well, and denies every other call without a prompt. An allow rule `Edit(/**)` confines the file tools' writes to the directory of the settings. Shell commands are checked by their own rules, so a command such as `bun` can still write elsewhere.
- Goals, as [Design goals and principles](261117_062916-design-principles.md#goals) defines them:
  - maintainability and extensibility, since a builder who knows only the skill and the documentation should be able to build an app, and the trials show where that fails;
  - observability, since every problem a trial meets is recorded where the user and the Agent can triage it, and the trials themselves stay in the repository's history.

## Decision

### The skill

- `skills/rack42u/SKILL.md` in this repository is a skill for agents that build apps on rack42u. An app that depends on rack42u through git has it at `node_modules/rack42u/skills/rack42u/`, and copies that directory into its own `.claude/skills/` to give it to an agent, as getting started then says.
- It holds what an agent needs before it writes code:
  - what rack42u is, in a few lines, and where the documentation is, `node_modules/rack42u/docs/`;
  - the workflow of an app: connectors, devices, the rack, tests on the bench, `rack dev`, and `status()`;
  - the rules that keep devices swappable, such as no imports between devices, data that survives `structuredClone`, background work in `activate`, and needs only below;
  - the pitfalls that the documentation and the trials found;
  - which document answers which question.
- It points to the documentation rather than repeating it. It is documentation for models, so the global rules apply to it: the documentation gate checks its links, each of its claims links to the section of a guide or of the reference that holds it, and a code block whose first line is `// <path>` belongs to an app that a test runs.
- `files` in `package.json` gains `docs` and `skills`, so that a packed package carries them, as a git install does.

### Issue templates

- `.github/ISSUE_TEMPLATE/` holds GitHub issue forms:
  - `trial.yml`, "Problem in a trial app": the app; what the agent was doing; what happened, with the command and its output; what it expected; where the skill, the documentation, or the API fell short; how it worked around it; how much it cost, blocked, slowed, or minor; and the rack42u commit.
  - `bug.yml`, "Bug": the rack42u version or commit, the Bun version, the system, the steps, what was expected, what happened, and the log.
  - `documentation.yml`, "Documentation": the document and section, what is wrong or missing, and what would help.
  - `feature.yml`, "Feature": the problem, the proposal, and the alternatives.
  - `config.yml`, which turns off blank issues, so that every issue starts from a form.
- The forms apply the labels `bug`, `documentation`, and `enhancement`, and a new label, `trial`, for issues that trials found.

### The trial apps

Four apps, each typical of a kind of program, and each reaching a different part of rack42u:

| App | What it is | What it reaches |
|---|---|---|
| `links` | A link shortener: an HTTP API that stores links and redirects to them | The HTTP panel, `sqlite`, errors as HTTP statuses, tests on the bench, and a hot reload |
| `chat` | A chat room over WebSocket | WebSocket through the HTTP panel, events, recent messages in `memkv`, and sockets kept across a hot swap |
| `watcher` | Checks a list of URLs on a schedule, and reports the ones that change or fail | Background work in `activate`, a device watchdog, events between devices, a scanned rack with one `own` copy per URL, and recovery from a crash and a hang |
| `files` | A file store: upload, list, and download | Bodies that stream through the HTTP panel, size limits, a device that writes files, and a cold swap |

- Each app's spec says what the app does, and how to check it: tests of its devices on the bench, and a script that runs its rack and checks its answers. It says nothing about how to use rack42u.

### The trials folder

The trials live in this repository, in `.agents/trials/`, beside the decision records, so that their specs, the apps the agents wrote, and their logs are part of rack42u's history. The Agent prepares it:

- `CLAUDE.md`, for the trial agents: each builds one app in its own subfolder, knows rack42u only from the skill and from `node_modules/rack42u/`, doesn't change rack42u, doesn't run `git`, records in `TRIAL.md` every problem it meets, and records it too when it has to read rack42u's source to go on.
- `.claude/settings.json`:
  - `claudeMdExcludes` skips rack42u's own `CLAUDE.md`, at the repository's root and in every app's `node_modules/rack42u/`, so the trial agents read only the folder's `CLAUDE.md` and the user's own.
  - The permission mode is `dontAsk`, and the allow rules list only: running the workflow, editing files in the folder, `Edit(/**)`, and the commands `bun`, `bunx`, `curl`, and those that list and read files. Every other call is denied without a prompt.
- `.gitignore`, so that git tracks the specs, the apps' code, `package.json`, the logs, and `issues.json`, and none of what the apps install and write as they run: `node_modules/`, `.rack/`, `data/`, `*.db` and its `-shm` and `-wal` files, `bun.lock`, logs, `.env`, and `.claude/settings.local.json`.
- `.claude/skills/rack42u`, a symbolic link to the repository's `skills/rack42u/`, so that the trials use the skill of the commit under trial.
- One subfolder per app, `links/`, `chat/`, `watcher/`, and `files/`, with its spec as `SPEC.md`. The trial agent adds rack42u to it as the documentation says, from this repository at the commit under trial: it adds `git+file://<repository>#HEAD`, pins in `package.json` the commit that Bun reports, as the documentation advises, and records the commit in `TRIAL.md`.
- `.claude/workflows/rack42u-trials.js`, the workflow:
  - It runs the four trial agents, two at a time, on Sonnet 5.5, a capable model that leans on the documentation more than the most capable one would. Each builds its app as `SPEC.md` asks, keeps `TRIAL.md` while it works, and returns its problems in the fields of the trial form, with a summary of what works and what doesn't.
  - A last agent, on Sonnet 5.5 too, merges the problems that are the same across the apps, and writes them to `issues.json`.
  - It needs a token budget, which the user gives when starting it, 2 million output tokens for the four trials and the merge, and doesn't start without one. It starts no further trials once the rest of the budget can't cover them and the merge.
- `biome.json` leaves `.agents/trials/` out, so the apps' code, which the trial agents write in their own style, doesn't fail rack42u's lint. `bun test`, the decision gate, and the type check pass over it already.

### How the trials run

1. The user starts Claude Code in `.agents/trials/`, and asks it to run the workflow `rack42u-trials`, with a budget of 2 million output tokens.
2. The workflow runs as above; the user can watch it with `/workflows`.
3. When it has ended, the Agent, in a session at the repository's root, commits `.agents/trials/` as the trials left it, in a commit of its own.
4. It then reads `issues.json` and the four `TRIAL.md` files, and files the issues.

### Filing the issues

- The Agent files one issue per distinct problem in this repository, from the trial form, with the label `trial` and one of `bug`, `documentation`, and `enhancement`. Each issue names the apps that met the problem, quotes their commands and output, and links to their files at the commit of step 3.
- A problem that only the trial agent's own mistake caused is filed when the skill or the documentation could have prevented it, and otherwise left out, with a line in the report.
- The Agent files nothing else, closes no issue, and reports the list of issues to the user. The user and the Agent then triage and solve them together; each fix follows the usual rules, with a decision where one is required.
- A later round of trials, after fixes, runs the same way in the same folder, and its commit shows what changed.

### Bounds and failures

- Four apps, one trial agent each, at most two at a time, within the token budget of the run.
- A trial agent that stops before its app works leaves its log, and what it couldn't finish is a finding too.
- A call outside the allowed tools, or an edit outside the folder, is denied; the denial is a finding of the trial setup, not of rack42u, unless the documentation told the agent to make that call.
- What the setup can't prevent, which the report states when it matters:
  - Node's lookup of packages climbs to the repository's own `node_modules/`, so a trial app can import a package that it never declared and still work.
  - A command that the agent may run, such as `bun`, can still read or write outside the folder; `CLAUDE.md` asks the agent not to.
  - The session sees this repository's git status and recent commit subjects.

## Alternatives

- **The trials folder outside the repository:** the trials wouldn't be part of rack42u's history, which the user ruled out.
- **The trials folder at the repository's root, as `trials/`:** easier to find, but `bun test` would run the apps' tests as rack42u's own, and the folder would mix process material with the code; `.agents/` already holds such material, and dot directories stay out of `bun test` and the gates.
- **A workflow run from the repository's root session:** the simplest to start, but its agents would read `AGENTS.md`, so the trials would show less of what a builder who knows only the documentation meets, and that session's permissions would leave their tools unconfined.
- **Headless sessions, `claude -p`, one per app:** independent too, with a cap on the spend and the turns of each session, but they run out of sight, in log files, and the user chose the workflow.
- **The user builds the apps:** a real newcomer's view, but slow, and the user asked for an agent.
- **Problems recorded in a file of this repository only:** the user asked for GitHub issues; the logs stay in the repository too.
- **One larger app:** it would reach fewer parts of rack42u, and its problems would pile on each other.
- **Trials without the skill:** they would test the documentation alone, but agents that build apps will have the skill, which the user asked for.
- **The skill as a Claude Code plugin, or in `~/.claude/skills/`:** a plugin needs a marketplace to install from, and a skill in the user's home directory applies to every project and every rack42u version. A copy in the app follows the app's own version of rack42u.

## Impact

- Spend: the token budget that the user gives the run.
- New in the repository: `skills/rack42u/`, `.github/ISSUE_TEMPLATE/`, `.agents/trials/` with its `CLAUDE.md`, settings, `.gitignore`, workflow, and specs, a section of getting started on agents, `docs` and `skills` in `files`, and `.agents/trials` left out of `biome.json`. The documentation gate also reads `skills/`.
- A commit per round of trials, with the apps' code and logs.
- New on GitHub: the label `trial`, and the issues.
- `AGENTS.md`: the repository structure gains `skills/`, `.github/ISSUE_TEMPLATE/`, and `.agents/trials/`, and "Current state" the trials.
- Follow-up: the triage and the fixes of the issues.

## Implementation

- `.github/ISSUE_TEMPLATE/`: `trial.yml`, `bug.yml`, `documentation.yml`, `feature.yml`, and `config.yml`, which turns off blank issues. GitHub uses the forms once they are on `main`.
- The label `trial` exists on GitHub since 2026-11-19.
