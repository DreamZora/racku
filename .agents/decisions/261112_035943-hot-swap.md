# Decision: Every device supports hot swap and hot reload

Status: accepted

## Background

- The user requires every component (device) to support:
  - Hot swap: insert, remove, and replace devices while the rack runs.
  - Hot reload: change code and have it take effect without restarting the process.
- In Bun, reloading a module inside the process does not yield complete new code (see [Evidence](#evidence)), so a dedicated mechanism is required.

## Decision

### One swap process

- Hot swap (inserting, removing, and replacing devices) and hot reload (giving the same device new code) use one swap process. Hot reload amounts to fitting a device of the same model with new firmware.

### Firmware

- Each device is built separately into one bundle with `Bun.build`, and the file name includes the content hash (`[name]-[hash].[ext]`). The hash is the firmware version.
- Third-party dependencies and the framework itself are not built into the bundle (they are marked external).
- In development mode the build watches for file changes and rebuilds on change, swapping only the devices whose hash changed. Editing a shared connector changes the hash of every device that uses it, and those devices are swapped together in one batch.

### The main thread never loads device code

- The rack main thread runs only the backplane, the slot state machine, power sequencing, the panel, and the management bus.
- The rack manifest references devices by path, and the main thread does not import any device code. Once the main thread has loaded a device, it keeps that old code forever.
- After a device loads it reports its model, its height, and its `needs`/`provides`, that is, its FRU information, and the rack validates against it.

### Installation forms

| Form | Runs in | Swap method | Suits |
|---|---|---|---|
| `sled` (default) | One Worker per device | Start a new Worker; terminate the old Worker once it has finished the calls it holds | Most devices |
| `inline` | The rack main thread | import the new bundle; delete the old bundle from `require.cache` | Small devices that are sensitive to call latency |
| `chassis` | A child process | Start a new child process; the old process exits once it has finished the calls it holds | Native extensions, untrusted code, and devices that need isolation from memory exhaustion or crashes |

- `sled` is the default because terminate reliably releases every resource a device created, including timers, listeners, and connections.
- `inline` has no such guarantee. Device resources must be bound to the `ctx.signal` the rack provides, which aborts at power off; otherwise the old instance keeps running and cannot be reclaimed.

### The swap sequence

Principle: requests are make-before-break, background tasks are break-before-make.

1. Load the new firmware into a standby instance in the same slot, read its FRU information, and check compatibility: ports that other devices are using must not disappear and must not change schema.
2. The new instance runs `powerOn` and `selfTest`. It stays in standby and receives no requests.
3. Handover:
   1. The old instance runs `deactivate` and stops its background tasks.
   2. If the device has in-memory state: pause dispatching calls to the slot and buffer new arrivals; once in-flight calls have completed, the old instance runs `snapshot()` and the new instance runs `restore(state, fromVersion)`.
   3. The new instance runs `activate`, and the backplane switches the slot's routes to the new instance in one step.
4. The old instance runs `powerOff` after it finishes the remaining calls, and is then reclaimed.
5. If any of steps 1 through 3 fails, discard the new instance, and the old instance runs `activate` again and keeps serving; the slot is marked degraded and the error is reported over the management bus.

### Lifecycle

- The hook order is `powerOn` → `selfTest` → `activate` ⇄ `deactivate` → `powerOff`, where `snapshot` / `restore` are optional.
- Background tasks such as timers and queue consumers may start only after `activate` and must stop at `deactivate`. The reason is that during a swap the old and new instances briefly coexist, so a background task started in `powerOn` would run twice.

### The rack owns external connections

- The panel (`Bun.serve`) is owned by the rack main thread. When devices change, routes are updated with `server.reload()`.
- The WebSocket handler is a fixed forwarding layer that always hands messages to the device currently installed, so a swap never drops existing connections.

### Live manifest edits and rack upgrades

- When the rack manifest is edited while the rack runs, the rack diffs the old and new manifests, then inserts, removes, and replaces devices and edits patches (reconcile). Replacement follows make-before-break order.
- If a device is still depended on by the devices above it, removing it is rejected unless the same edit supplies a replacement device.
- The rack itself (the backplane code) cannot be replaced inside the process. To upgrade, start a new process that listens on the same port with `reusePort`, then power the old process off in order.

## Evidence

Measured on 2026-11-12 on the local machine with Bun 1.3.13 (Linux). The probe script was not committed to the repository.

- Re-importing inside the process (adding a `?v=` query parameter, or running `delete require.cache[path]` first) re-executes only the entry file, and the other files the entry file imports stay on the old version.
- Importing a device after building it into a hashed bundle yields new code, including its transitive dependencies. Building a simple device takes about 7ms.
- Reloading 40 times with each version holding about 8MB of state: RSS grows from 39MB to 350MB when the old `require.cache` entries are not deleted, and only from 38MB to 66MB when they are.
- A Worker cold start takes about 4ms, an empty device takes about 3MB of RSS, and one small data round trip takes about 11µs. For comparison, an in-process call plus `structuredClone` takes about 1µs.
- An uncaught exception in a Worker surfaces on the main thread as an `error` event, and the main thread and the other Workers are unaffected.
- After `server.reload()` replaces the routes, established WebSocket connections stay open.
- With `Bun.serve({ reusePort: true })`, a second process can bind the same port while the first process is still listening.

## Alternatives

- **`bun --hot`**: it applies to the whole process, cannot swap devices one at a time, and provides no compatibility check, make-before-break, or rollback on failure. It is used only as a development convenience, not as the framework's hot reload mechanism.
- **Re-import directly inside the process (adding `?v=` or deleting `require.cache` entries)**: it refreshes only the entry file, and transitive dependencies stay on the old code (see [Evidence](#evidence)).
- **Let only devices in Workers and child processes support hot swap, not devices on the main thread**: this was the initial plan, and it does not meet the "every component supports it" requirement.
- **Run every device on the main thread**: calls are fastest, but whether resources are released depends entirely on the device itself, and one misbehaving device leaves old code running.

## Impact

- By default each device costs one more Worker (about 3MB of memory) and about 10µs more per call.
- Data on ports must be copyable by structured clone; errors must be serializable, meaning they carry an error code and data; timeouts and cancellation (deadline, AbortSignal) must cross the backplane.
- Device authors must follow the lifecycle rules: background tasks may start only after `activate`, and `inline` device resources must be bound to `ctx.signal`.
- State handover, live manifest edits, the `chassis` form, and whole-rack replacement with `reusePort` can be delivered in stages, but the swap process itself must be in place from the first version.

## Confirmation

- "Every device supports hot swap and hot reload" is an explicit user requirement.
- The implementation mechanism was designed by the Agent from measured results. On 2026-11-12 the user authorized the Agent to decide routine decisions on its own, and this decision was set to `accepted` on that basis.
