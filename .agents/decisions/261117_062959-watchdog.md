# Decision: Watchdog

Status: accepted

## Background

- A device can hang without crashing, in two ways:
  - **Its event loop is blocked**: a loop that never ends, a long synchronous computation, `Atomics.wait` without a timeout, or a long call into native code, such as a large SQLite query. Nothing else runs in its Worker, not even the Worker host.
  - **One of its work loops stops**: a promise that never settles, a consumer that waits for input forever, or a task that stops scheduling itself. The event loop still runs and the Worker host still answers, so only the device knows whether its work makes progress.
- The rack notices neither. Calls to a hung device wait until their deadlines and fail with `RACK_TIMEOUT`, and its background work stops without a trace. The README lists watchdogs for hung devices as not supported yet.
- [Rack runtime architecture](261112_035942-rack-architecture.md#reliability-and-management) names a watchdog that resets a device when its heartbeat times out. [Fallback, rollback, and update history](261117_005743-fallback-rollback-and-history.md#passive-fallback) expects the watchdog to add a reason to fall back, through the same mechanism.
- On 2026-11-17 the user agreed to a watchdog that devices keep feeding.
- Embedded systems split supervision the same way. ESP-IDF's task watchdog, for example, watches each CPU's idle task, which starves when another task hogs the CPU, and lets tasks subscribe and feed it themselves.
- Goals, as [Design goals and principles](261117_062916-design-principles.md#goals) defines them: reliability, since a hang is detected, contained, and recovered from; and observability, since every bite is reported with its cause.

## Decision

### Two kinds of watchdog

- **The event-loop watchdog**: every device instance has one. The Worker host feeds it from a timer, so it starves only when the device's event loop is blocked. Device code does nothing for it.
- **Device watchdogs**: a device arms one for each work loop that it wants watched, and feeds it from that loop.

  ```ts
  activate(ctx, scope) {
    const dog = scope.watchdog(5_000, "poller");
    void (async () => {
      while (!scope.signal.aborted) {
        await pollOnce(ctx);
        dog.feed();
      }
    })();
  },
  ```

  - `scope.watchdog(ms, name?)` arms a watchdog that bites when `feed()` isn't called for `ms` milliseconds, and returns `{ feed(), cancel() }`.
  - `ms` is at least 1 000; shorter timeouts would trip on garbage-collection pauses and late timers. A smaller value throws a `RangeError`.
  - `name` appears wherever the watchdog is reported. It defaults to `watchdog 1`, `watchdog 2`, and so on, in the order they were armed.
  - `cancel()` disarms the watchdog, for example when a job finishes.
  - An instance can have at most 16 device watchdogs armed. Arming another throws a `RangeError`.
- Watchdogs watch an instance while it is active, from the end of `activate` to the start of `deactivate`. Hooks are bounded by `hookTimeout` instead, and a retiring instance by `drainTimeout`. Device watchdogs disarm on `deactivate`, like the scope's timers.

### Feeding and checking

- A feed increments a counter in memory that the Worker shares with the main thread. It sends no message, so feeding often costs nothing measurable.
- The main thread reads each counter four times per timeout, on its own monotonic clock. A watchdog therefore bites between 1 and 1.25 times its timeout after its last feed, and a change of the system clock can't make it bite.

### Biting

- When a watchdog bites:
  - The instance's calls in flight fail at once with `RACK_DEVICE_FAULT`, and its slot reports `resetting`. Calls that arrive during the reset fail with `RACK_LINK_DOWN`, as during a crash reset.
  - The rack terminates the instance's Worker. Once the Worker has closed, the bite goes the way of a crash: the device resets from the same firmware, or falls back to its known-good firmware while on probation.
- The error is `RACK_DEVICE_FAULT`, and its `data` names the watchdog: `{ watchdog: "poller", timeout: 5000 }`, or `{ watchdog: "event loop", timeout: 10000 }`. It appears as the slot's `error`, in the `fault` event, in the log, and in the history record of a fallback. Callers branch on the same code as for a crash.
- Bites count toward the crash limit. The limit's window is 60 s, or four times the longest timeout of the device's watchdogs if that is longer. A device that hangs again after every reset therefore ends up `faulted`, whatever its timeouts.
- A Worker that is blocked in native code closes only when that call returns, as the evidence below shows:
  - If the Worker hasn't closed within `hookTimeout` of the bite, its slot becomes `faulted`, and the rack logs that a thread is stuck.
  - The slot then stays `faulted` until a swap or a restart succeeds. Two instances of the device never run at the same time.
  - Only a restart of the rack reclaims a thread whose native call never returns.

### Configuration and observation

- The start option `watchdog` sets the timeout of every event-loop watchdog, 10 000 ms by default. A blocked event loop is caught within 10 to 12.5 s, which leaves room for the longest synchronous work a device should do. A builder whose devices block for longer, for example with large SQLite queries, raises it.
- `watchdog: 0` turns off every watchdog, device watchdogs included, for example while a debugger holds devices at breakpoints. `rack start --no-watchdog` and `rack dev --no-watchdog` do the same.
- `status()` lists each device's armed watchdogs, the event-loop watchdog first: `watchdogs: [{ name, timeout, lastFed }]`. `lastFed` is when the rack last saw a feed, a millisecond timestamp, at most a quarter of the timeout late.
- `metrics()` reports each device's event-loop delay, which the timer of the event-loop watchdog measures: `loop: { delayMs, maxDelayMs }`, the delay of its last tick and the largest since the instance booted. A rising delay shows a device that falls behind before any watchdog bites.

## Evidence

Measured with Bun 1.4.4 on 2026-11-17. A Worker fed a shared `Int32Array` counter from a 50 ms timer and then hung; the main thread read the counter, called `terminate()`, and waited for the Worker's `close` event:

| Hang | Feeds during the hang | `close` after `terminate()` | CPU afterward |
|---|---|---|---|
| `while (true) {}` | 0 in 1 s | 9 ms | idle |
| `Atomics.wait` without a timeout | 0 in 1 s | 1 ms | idle |
| An endless chain of microtasks | 0 in 1 s | 289 ms | idle |
| A SQLite query of about 3.7 s, terminated 1 s in | 0 in 0.9 s | 2.8 s, when the query returned | idle |
| A read from a FIFO without a writer, terminated 1 s in | 0 in 0.9 s | 2.0 s, when a writer unblocked it | idle |

- Every kind of hang stops the feeds, so a counter is enough to detect it.
- `terminate()` stops a Worker that hangs in JavaScript within milliseconds, and one that hangs in native code only when the native call returns. Until then, the SQLite query kept a whole CPU core busy.
- `Bun.nanoseconds()` counts from the start of each thread, so the main thread can't compare a Worker's value with its own. `performance.timeOrigin + performance.now()` agreed across threads within 3 ms, but it follows the system clock at each thread's start. Comparing counters on the main thread's clock avoids both problems.

## Alternatives

- **Device watchdogs only**: one mechanism. But most devices have no work loop, and each would need a timer only to prove that its event loop runs. A device that forgot it would never be watched.
- **The event-loop watchdog only**: no device code at all. But a work loop that stops while the event loop runs would go unnoticed, and that hang is the one only the device can see.
- **Ping the Worker host with messages instead of shared counters**: no shared memory. But it costs a message per check for every device, and the main thread's own work delays the pings.
- **Declare device watchdogs in the device spec**: the rack would know them before activation and arm them itself. But a device with several loops needs several declarations, which drift apart from the feeding code. Arming in `activate` keeps both in one place.
- **Supervise the runs of `scope.every` automatically**: no feeding code for loops built on it. But many loops aren't, such as stream readers and socket loops, and each run would still need a deadline.
- **A default of 30 s, the same as `callTimeout`**: fewer resets of devices with long synchronous work. But a hang would hold every caller for its full timeout before recovery starts.
- **A per-device timeout for the event-loop watchdog**: a device with long synchronous work could ask for more time. But how long that work takes depends on the workload, which the builder knows better than the device. One rack-wide option is enough until a device proves it needs its own.
- **Reset at once, without waiting for the Worker to close**: service would come back sooner after a hang in native code. But the stuck thread keeps its CPU and its resources, a device that declares `swap: "cold"` would run twice, and repeated hangs would leak threads without bound.
- **A new error code, `RACK_WATCHDOG`**: easier to branch on. But callers that already handle `RACK_DEVICE_FAULT` would miss hangs. The error's `data` names the watchdog without a new code.

## Impact

- A device that hangs comes back by itself, and falls back to its known-good firmware when the hang follows an update.
- Changes to current behavior:
  - A device whose event loop stays blocked for longer than `watchdog`, 10 s by default, is reset. Builders with longer synchronous work raise the option.
  - The window of the crash limit grows with long watchdog timeouts. With the defaults it stays 60 s.
- New public API:
  - `scope.watchdog()` on the scope that `activate` receives.
  - The start option `watchdog`, and the `--no-watchdog` flag.
  - `watchdogs` in `SlotStatus`, `loop` in the entries of `metrics()`, and the `data` of a bite's error.
- Only the `sled` form exists today. Decisions for later forms have to say how they supervise:
  - A `chassis` device runs in a child process, which can be killed even inside native code.
  - An `inline` device runs on the main thread, which no watchdog in the same thread can watch.
- The rack process itself stays unsupervised by the rack; [Design goals and principles](261117_062916-design-principles.md#reliability-practices) assigns it to the service manager.
- Follow-up work once this decision is accepted:
  - The shared counters in `src/instance.ts` and `src/worker.ts`, the checks and the bite in `src/rack.ts`, `scope.watchdog()` in `src/device.ts` and `src/worker.ts`, and the flag in `src/cli.ts`.
  - Tests:
    - a blocked event loop, an endless chain of microtasks, and an unfed device watchdog each bite and reset the device
    - a bite during probation falls back
    - a device that hangs after every reset ends up faulted
    - a Worker stuck in native code faults its slot after `hookTimeout`
    - `cancel()` and `deactivate` disarm, and `watchdog: 0` turns every watchdog off
    - `status()` and `metrics()` report the watchdogs and the loop delay
  - README: the watchdog, the option, the flag, and the new crash-limit window.

## Implementation

- `src/protocol.ts` lays out the memory each instance shares with the main thread, `SHARED_SERVING`, `SHARED_LOOP`, and `SHARED_WATCHDOGS`, and holds `WATCHDOG_LIMIT`, `WATCHDOG_MIN`, and the `WatchdogNotice` a Worker sends when its device arms or cancels a watchdog.
- `src/worker.ts`:
  - `feedLoop()` feeds the event-loop watchdog from a timer that ticks 8 times per timeout, between 100 ms and 1 s apart, and measures the delay of each tick. Without watchdogs the timer still measures the delay, once a second.
  - `armWatchdog()` implements `scope.watchdog()`. A cancelled watchdog, and every watchdog of a scope that stops, tells the main thread.
- `src/instance.ts` checks the watchdogs:
  - `hook()` starts the checks when `activate` succeeds and stops them before it sends `deactivate`, so every path that activates or deactivates an instance gets them.
  - Each watchdog has an interval of a quarter of its timeout, and bites after four checks in a row without a feed. Counting checks instead of comparing clock readings keeps a change of the system clock, or a busy main thread, from making a watchdog bite early.
  - `kill()` terminates the Worker as `terminate()` does, so the instance is gone at once, and reports whether its thread stopped within a timeout.
- `src/rack.ts`:
  - `onBite()` fails the calls in flight, kills the instance, and keeps the slot busy until the thread has stopped, so that no swap can start a second instance meanwhile. Probation timers of the slot's group pause during that wait, so that firmware that hung can't become known-good.
  - When a swap is running at the bite, the swap handles the slot, and the bite is counted at once, as a crash would be.
  - A bite while the rack starts fails the start with `RACK_DEVICE_FAULT`, as a crash does.
  - `#crashed()` holds the recovery that crashes and bites share. `crashWindow()` computes the window of the crash limit from the longest watchdog timeout of the instance that crashed or bit.
  - The start option `watchdog`, and `watchdogs` in `status()`.
- `src/cli.ts` adds `--no-watchdog` to `rack start` and `rack dev`.
- `test/watchdog.test.ts` tests the decision. Sixteen deliberate breaks of the mechanisms, such as never biting, feeding nothing, watching through `deactivate`, or resetting before the thread stops, each made one of its tests fail.

## Confirmation

- The user accepted this decision on 2026-11-17. The user required that devices keep feeding the watchdog.
- The Agent added the event-loop watchdog that the Worker host feeds, the defaults, and the window of the crash limit, which the user accepted as drafted.
