# Decision: Position the project as an application-agnostic base component framework

Status: accepted

## Background

- rack42u uses the 42U standard rack as an analogy: the rack provides standard slots, power, and a backplane, and devices plug in through standard connectors and then work together.
- Use cases include but are not limited to backends, frontends, desktop, IoT/edge gateways, and automation, so the framework cannot presuppose an application type.

## Decision

- rack42u provides only two kinds of things:
  - **Rack runtime**: loading devices, backplane communication, power sequencing, hot swap, and management.
  - **Standard base components**: common interface standards, plus standard devices that can be used directly, such as configuration, storage, KV, timing, and external ports.
- Which devices are plugged into the rack, and whether they are assembled into a backend, a frontend, a desktop, or another application, is decided by the builder.
- The core runtime contains no logic for a specific application type and does not depend on any standard device; standard devices are selected as needed.
- The technology stack is based on Bun: TypeScript and ESM, with Bun serving as runtime, package manager, and test runner at the same time. Prefer Bun's built-in capabilities, such as `Bun.serve`, `bun:sqlite`, `Bun.SQL`, `Bun.redis`, `Bun.s3`, and Worker.
- The baseline version for development and validation is Bun 1.3.13, confirmed on this machine on 2026-11-12; the minimum supported version is decided in the P0 stage.

## Alternatives

- **Target a single scenario (for example, only a web backend)**: the scope would be easier to control, but the user explicitly requires coverage of backends, frontends, desktop, and other scenarios, with the builder deciding what to plug in.

## Impact

- The core must be independent of application scenarios: capability for a specific scenario can only be built as a standard or third-party device, never placed in the core.
- How scenarios such as frontend and desktop fit into a rack is not designed yet, for example whether the rack runs on the browser side and how a desktop shell hosts the rack. Write separate decisions when the corresponding standard devices are built.
- The code depends on Bun-specific APIs, so it cannot run directly on Node.
